**系统定位**

把项目定义成：

**Text2SQL 评测与对比平台**

目标不是单纯“生成 SQL”，而是提供完整能力：

- 单题测试
- 批量评测
- SQL 执行验证
- 失败分析
- 闭源模型 vs 开源模型对比
- SFT 模型 vs RL 模型对比
- 后续支持 fallback / 智能路由

---

**1. 技术栈**

**前端**
- `Next.js`
- `TypeScript`
- `Tailwind CSS`
- `shadcn/ui`
- `TanStack Table`
- `ECharts` 或 `Recharts`

**后端**
- `FastAPI`
- `SQLAlchemy`
- `Pydantic`
- `Alembic`

**任务系统**
- `Celery`
- `Redis`

**数据库**
- `PostgreSQL`

**模型接入**
- 闭源模型：OpenAI-compatible API
- 开源模型：`vLLM serve`

**部署**
- 本地开发：`Docker Compose`
- 后续上线：容器化部署

---

**2. 整体架构**

```text
[ Next.js Frontend ]
        |
        v
[ FastAPI API Layer ]
        |
        +--> [ PostgreSQL ]
        |
        +--> [ Redis ]
        |
        +--> [ Celery Worker ]
                 |
                 +--> ClosedModelProvider
                 |
                 +--> OpenModelProvider(vLLM)
                 |
                 +--> SQL Executor
                 |
                 +--> Evaluator / Failure Analyzer
```

**5. 模型抽象设计**

核心思想：

业务层永远只认 `model_id`，不关心底层是闭源还是开源。

**5.1 抽象接口**

```python
class BaseModelProvider:
    def generate_single(self, prompt: str, config: dict) -> dict:
        ...

    def batch_generate(self, prompts: list[str], config: dict) -> list[dict]:
        ...

    def health_check(self) -> dict:
        ...
```

**5.2 `ClosedApiProvider`**
支持：
- OpenAI
- DashScope
- 其他 OpenAI-compatible 服务

配置：
- `base_url`
- `api_key_env`
- `model_name`

**5.3 `VLLMProvider`**
支持：
- 本地 `vllm serve`
- 你的 SFT/RL merged model

配置：
- `base_url`
- `model_name`

**5.4 `ModelRouter`**
根据 `model_id` 查表，自动选 provider。

逻辑：
- 查 `models`
- 判断 `provider_type`
- 实例化 provider
- 返回统一结果格式

- `GET /models`

- `POST /models/{id}/health`

**6.2 数据集**


**6.6 失败分析**
- `POST /tasks/failure-analysis`
- `GET /runs/{run_id}/failures`

**7. 任务流设计**

**7.1 单题测试**
1. 前端提交问题
2. API 创建 `task`
3. Celery worker 调模型
4. 可选执行 SQL
5. 保存 prediction / execution
6. 返回结果

**7.2 批量评测**
1. 前端选择模型和数据集
2. API 创建 `task`
3. worker 逐条推理
4. 生成 `predictions`
5. 调 SQL 执行评测
6. 聚合 metrics
7. 保存 `run`

**7.3 模型对比**
1. 同一数据集分别跑 left / right model
2. 生成两个 `run`
3. 聚合对比指标
4. 输出 diff 报告

**10. 统一返回格式**

无论闭源还是开源，后端都转成统一结构：

```json
{
  "reasoning": "...",
  "action_type": "sql",
  "action_body": "SELECT ...",
  "raw_output": "...",
  "latency_ms": 1234,
  "provider": "vllm"
}
```

这样评测、执行、前端展示都不用关心底层差异。
